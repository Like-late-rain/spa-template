# 单一职责原则 (Single Responsibility Principle - SRP)

## 定义

一个类应该只有一个引起它变化的原因，即一个类只负责一项职责。

## 核心思想

每个模块、类或函数应该只做一件事，并把它做好。

## 示例对比

### ❌ 不好的实践 (bad.tsx)

`UserProfileBad` 组件违反了SRP，因为它承担了太多职责：

1. **数据获取** - 调用API获取用户数据
2. **数据验证** - 验证邮箱和电话号码
3. **本地存储** - 管理localStorage
4. **日期格式化** - 格式化日期显示
5. **电话格式化** - 格式化电话号码
6. **UI渲染** - 展示用户界面

**问题：**

- 代码难以测试（需要mock多个依赖）
- 代码难以复用（格式化逻辑无法在其他组件使用）
- 修改任何一个功能都可能影响其他功能
- 违反了"高内聚，低耦合"的原则

### ✅ 好的实践 (good.tsx)

将职责分离到不同的模块：

1. **UserValidator** - 只负责数据验证
2. **UserStorage** - 只负责本地存储
3. **UserApiService** - 只负责API调用
4. **DateFormatter** - 只负责日期格式化
5. **PhoneFormatter** - 只负责电话格式化
6. **useUser** - 只负责用户数据管理
7. **UserInfo** - 只负责用户信息展示
8. **UserProfileGood** - 只负责组合和布局

**优点：**

- ✅ 每个模块职责单一，易于理解
- ✅ 易于测试（可以独立测试每个模块）
- ✅ 易于维护（修改一个功能不影响其他功能）
- ✅ 高复用性（格式化工具可在其他组件中使用）
- ✅ 符合"高内聚，低耦合"原则

## 实际应用场景

### 什么时候应该拆分？

当一个组件/类有以下情况时，考虑拆分：

- 有多个修改它的理由
- 包含多个不相关的功能
- 难以命名（需要用"和"来描述它的功能）
- 代码行数过多（>200行）

### React中的最佳实践

1. **将业务逻辑抽离到自定义Hook**
2. **将格式化逻辑抽离到工具函数**
3. **将API调用抽离到服务层**
4. **将UI拆分成小组件**
5. **将验证逻辑抽离到验证器**

## 总结

单一职责原则是SOLID原则的基础，遵守SRP可以让代码更易于维护、测试和扩展。在React开发中，应该将组件拆分成更小的、职责单一的单元。
